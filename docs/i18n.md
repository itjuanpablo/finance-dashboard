# Internacionalização — contrato

O Fluxo é local-first: cada pessoa roda a sua instância, com o próprio
`data/fluxo.db`. Por isso **idioma e moeda são fixos por instalação**, não há
seletor em runtime, provider de contexto nem estado de sessão. Trocar de idioma
é editar o `.env.local` e reiniciar.

```bash
# .env.local
NEXT_PUBLIC_FLUXO_LOCALE=es-AR     # pt-BR (padrão) | es-AR
NEXT_PUBLIC_FLUXO_CURRENCY=ARS     # opcional; derivado do locale
```

O prefixo `NEXT_PUBLIC_` é obrigatório: o Next embute o valor no bundle em build
time, então a mesma constante vale no servidor e no cliente sem hidratação.

## Módulos

| Arquivo | Papel |
|---|---|
| `lib/config.js` | `LOCALE`, `REGION` (moeda, símbolo, separadores), `CURRENCY` |
| `lib/i18n/index.js` | `t(key, vars)`, `tn(n, key)`, `catLabel`, `makeCatLabeler` |
| `lib/i18n/pt-BR.js` | dicionário de referência — toda chave nasce aqui |
| `lib/i18n/es-AR.js` | español rioplatense; voseo no imperativo |
| `lib/format.js` | `fmtMoney`, `fmtMoney0`, `fmtDate`, `fmtMonthLong`, `parseAmountToCents`… |
| `lib/categories.js` | `CAT` (chaves), semente, mapa de nomes históricos |

### Regras de uso

- **Nunca** escreva string visível direto no JSX. Use `t('area.coisa')`.
- **Nunca** use `toLocaleString('pt-BR', …)` nem `'R$'`. Use `lib/format.js`.
- Chave ausente devolve a própria chave (falha visível) e loga aviso em dev.
- Plural: chaves `.one` / `.other`, via `tn(n, 'import.tx')`.
- Convenção de chaves: `<area>.<coisa>[.variante]` — áreas em
  `lib/i18n/pt-BR.js`.
- Datas: nunca `new Date('2026-07-26')` (é UTC e desloca o dia em fuso
  negativo). Use os helpers de `lib/format.js`, que fatiam a string ISO.

## Categorias: chave estável, não nome

Até a v3.2 o identificador de categoria era o nome em português, copiado em
`transactions.category`, `rules.category`, `goals.category` e `bills.category`.
Isso impedia traduzir e quebrava quando o usuário renomeava.

Desde a v4 (`PRAGMA user_version = 4`):

- `categories.key` é o identificador — `'food'`, `'transport'`, `'to_review'`…
- `categories.name` guarda o nome **digitado pelo usuário**; para as 12 chaves
  canônicas ele é apenas um artefato de leitura: o nome exibido vem de
  `t('cat.<key>')`.
- `categories.custom = 1` marca categoria criada pelo usuário. Essas **não são
  traduzidas** — o "Dízimo" de alguém é o nome dele.
- Renomear categoria não mexe mais em transação, regra ou meta: a chave não muda.
  A cascata antiga saiu.

Use as constantes, nunca o literal:

```js
import { CAT, FLEX_CATEGORIES, NON_BUDGET_CATEGORIES } from '@/lib/categories';

tx.category === CAT.TO_REVIEW      // ✅
tx.category === 'A revisar'        // ❌ quebrado desde a v4
```

### Migração v3 → v4

Roda sozinha na primeira inicialização (`lib/db.js` → `migrateCategoryKeys`),
numa única transação, depois de gravar `data/backups/fluxo-pre-v4-*.db`.
Nomes históricos conhecidos (pt e es) viram chave canônica; o resto vira
`custom` com slug do nome. É idempotente.

## Contrato das APIs (v4)

`category` é sempre **chave**, na resposta e no corpo do request.

```jsonc
// GET /api/categories
{ "categories": [{
    "id": 1, "key": "food", "name": "Alimentação", "label": "Comida",
    "color": "#f97316", "emoji": "🍔", "archived": 0, "sort_order": 0,
    "custom": 0, "system": false,
    "txCount": 233, "monthlyAvg": 84210, "rulesCount": 12
}]}

// GET /api/transactions
{ "transactions": [{ "id": 1, "category": "food", /* … */ }],
  "categories":   { "food": "#f97316" },   // chave → cor
  "categoryEmojis": { "food": "🍔" } }     // chave → emoji
```

- `label` é o nome a exibir (traduzido se canônica, digitado se customizada).
- `POST /api/categories` recebe `{ name, color, emoji }` e deriva a chave via
  `slugifyCategory` (sempre `custom = 1`).
- `PATCH /api/categories` renomeando uma categoria **canônica** marca
  `custom = 1` mantendo a chave: a tradução deixa de se aplicar, o dado fica
  intacto.
- `moveTo` em `DELETE /api/categories` é chave, não nome.
